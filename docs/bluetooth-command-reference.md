# Bluetooth command reference

This is the command index for the Candybong Infinity firmware image
`nordic_tw3_230206_V1_3_RF447_9_OTA`.

The BLE Nordic UART Service handler is `ble_nus_data_handler()` at `0x35dc0`.
It recognizes packets whose first byte is `FF` and dispatches on byte `1`.
The byte at offset `2` is usually a length or reserved field; its exact use is
command-specific. Many packets sent onward by the firmware end with a
one-byte checksum generated by `calculate_checksum()`.

This inventory separates three things that are easy to confuse:

1. **Parser support** — the opcode has a branch in the firmware.
2. **Behavior understood** — the branch and its helper have been traced.
3. **Application support** — the Android app or a captured client is known to
   send the command. Static firmware analysis alone does not prove this.

For LED and animation tinkering, use the narrower
[safe lighting and animation allow-list](safe-lighting-commands.md). The
configuration, bridge, DFU, and undocumented frame-streaming commands below
are intentionally excluded from that list.

The parser therefore recognizes 38 `FF` opcodes in this firmware, not only the
commands currently listed in the Android proof of concept. It also has a
separate ASCII maintenance trigger, `@dfu`, which requests a system reset into
DFU mode.

## Common LED commands

### `FF 11`: LED on or restore

**Format**

```text
FF 11
```

**Properties**

- No color or speed field is consumed.
- If the shared RGB state is all zero, the handler replaces it with `FF FF FF`.
- Otherwise it restores the last shared RGB value.

**Behavior and mechanism**

The handler selects the normal solid-color state and schedules LED opcode `1`.
The timer dispatcher sends the shared RGBW state through
`set_led_group_color()`. This is an on/restore command, not a palette or
animation selector.

### `FF 12`: LED off

**Format**

```text
FF 12
```

**Properties**

- No color or speed field is consumed.
- It uses the selected LED group state.

**Behavior and mechanism**

The handler schedules LED opcode `0`. The timer dispatcher sends zero RGBW to
the selected group. It does not erase the saved RGB values, so `FF 11` can
restore the previous color.

## Feedback and response behavior

The BLE receive handler does not send a response for every command. A traced
`ble_uart_write()` call proves that the firmware constructed an outbound frame,
but static analysis alone does not prove that the frame is delivered as a
notification on the Nordic response characteristic rather than sent through
an internal or bridge path.

The most relevant response paths are:

| Incoming command | Traced outbound behavior | Measurement use |
|---|---|---|
| `FF 11`, `FF 12`, `FF 13`, `FF 14` | LED state/timer update only; no direct BLE reply in the handler | No firmware acknowledgment proven |
| `FF 15` | Calls `ble_led_send_reply()` after scheduling the palette color; constructs `FF 15 03 <three fields> <checksum>` | Strongest known solid-color feedback candidate |
| `FF E1`..`FF E6` | LED state/timer update only in the traced branches | No firmware acknowledgment proven; this includes direct RGB `FF E6` |
| `FF E7` | Emits a short `FF E7` packet with the supplied fields and checksum | Possible command feedback; capture should confirm delivery |
| `FF 16`, `FF 18`, `FF 1A`, `FF 21` | Constructs status, bridge, or parameter packets | Outbound status/bridge traffic, not ordinary LED acknowledgments |
| `FF A0`..`FF AF` | Several branches emit acknowledgments or frame readbacks | Protocol feedback, but the frame protocol is still conditional/unsafe |
| `FF C1`..`FF CA`, `FF AD` | Forwards configuration or bridge packets | Outbound relay traffic; not safe lighting feedback |
| `FF E9`, `FF EB`, `FF ED` | Echo or short control/status packets | Diagnostic/control feedback |

For the web latency probe, use `FF 15` so the GATT write, the matching
`FF 15 03` response, and the physical LED transition can be correlated. The
response is emitted after the firmware schedules the palette path; it is not a
proof that the LED driver has already finished updating. `FF E6` remains useful
as a separate arbitrary-RGB write test, but it has no traced command reply.

## Measurement, bridge, and control commands

These commands are parser-supported but are not ordinary direct LED controls.
They mainly construct packets for the firmware's UART/bridge path.

### `FF 16`: internal measurement/status conversion

**Format**

```text
FF 16
```

**Mechanism**

The handler calls `somthing_huhuhu()` at `0x38958`. That helper maps an
internal measurement into a small code from roughly `1..0x11` (or `0x20` for
an out-of-range condition), then constructs an outgoing packet equivalent to:

```text
FF 16 02 StatusCode Checksum
```

The source measurement and the meaning of each range are not identified yet.
No direct LED update is shown in this path.

### `FF 18`: fixed bridge request

**Format**

```text
FF 18
```

The handler calls `FUN_00038d50()`, which emits a fixed bridge packet:

```text
FF B4 02 01 03 Checksum
```

The higher-level purpose of this request is not established. It does not
directly update the LED buffer.

### `FF 1A`: parameter/timer request

**Format**

```text
FF 1A Value
```

The handler stores `Value * 100` in an internal timing/parameter field and
constructs an outgoing `FF 1A` packet containing the value. The exact physical
feature controlled by that parameter is not identified.

### `FF 21`: dynamic bridge/status packet

**Format**

```text
FF 21
```

The helper at `0x38dac` constructs a packet equivalent to:

```text
FF 21 09 01 03 <six dynamic bytes> Checksum
```

The six bytes are read from internal state/configuration. This appears to be a
status or bridge packet, not a direct color command.

### `FF AD`: subcommand bridge

**Format**

```text
FF AD ...
```

The parser accepts subcommands `1` and `2` at packet byte `3`. It uses random
or supplied state values and forwards a packet through `FUN_000388fc()`:

```text
FF AD 04 <subcommand> <mode> <value0> <value1> Checksum
```

The fields are decoded at the byte level, but their device-level meaning is
not established. This is likely a controller/bridge command rather than a
user-facing LED command.

### `FF E5`: scaling-state change

**Format**

```text
FF E5 00 Value
```

The parser copies packet byte `3` into the shared scaling field, but the traced
branch does not schedule a refresh or invoke the normal LED output routine.
It may be an intermediate/internal state command; a runtime capture is needed
to determine when its effect becomes visible.

### `FF E9`: echo with checksum

**Format**

```text
FF E9 <payload...>
```

The handler recalculates the checksum over the received buffer and sends the
buffer through the UART/BLE bridge. It is useful for link testing or protocol
diagnostics and does not drive the LEDs.

### `FF EB` and `FF ED`: frame/control requests

The parser recognizes both opcodes and emits short packets containing the
opcode, `02 00`, and a checksum. `FF ED` also calls the frame/output helper
`FUN_00029790()` before sending its packet. Their exact application-level
meaning remains unresolved.

## Configuration relay commands

The `C*` commands read or write groups of internal configuration bytes and
forward the values over the bridge. They are not part of the normal RGB LED
path.

| Command | Input handled | Forwarded data | Current interpretation |
|---|---|---|---|
| `FF C1` | Four bytes at packet offsets `3..6` | Status plus four stored bytes | Configuration/status update; the first value is range-checked against `0xCC` |
| `FF C3` | No meaningful input traced | Four stored bytes | Configuration readback |
| `FF C5` | Fourteen bytes at offsets `3..0x10` | Fourteen stored bytes | Configuration write followed by readback |
| `FF C6` | No meaningful input traced | Fourteen stored bytes | Configuration readback |
| `FF C7` | Fourteen bytes at offsets `3..0x10` | Fourteen stored bytes | Configuration write followed by readback |
| `FF C8` | No meaningful input traced | Fourteen stored bytes | Configuration readback |
| `FF C9` | No meaningful input traced | Fourteen mixed stored bytes | Configuration readback |
| `FF CA` | No meaningful input traced | Fourteen mixed stored bytes | Configuration readback |

The exact names of these settings, persistence behavior, and hardware function
are not recoverable from the BLE parser alone. Sending them experimentally may
change device configuration, so they should be treated as maintenance commands.

## A* frame and animation streaming commands

### Safety verdict

The `A*` family is RAM-backed frame streaming, not the configuration relay
family. In the traced paths, the firmware:

- copies incoming RGB triplets into three `0x300`-byte RAM planes;
- reads those planes back into RAM response packets;
- calls `FUN_00030cd0()` to send/display frame data; and
- uses `mem_zero()` (`0x264ba`) to clear response payload space.

No flash erase/write or `C*` configuration writer was seen in the A* branches
or their directly traced output helpers. That makes a correctly formed A*
transaction appear non-persistent. It does not make arbitrary packets safe:
the command-specific length is not validated before all fields are read, the
target field is not decoded, and malformed sequences can select an unintended
LED-controller address/state or leave the frame scheduler active. The outer
BLE receive copy is bounded, but that is not the same as validating an A*
packet.

`T` below is byte `2`, a provisional target/frame selector. Its application
meaning and valid values were not recovered. `I` is byte `3`, the chunk index.
RGB data is byte-interleaved as `R G B R G B ...`.

| Command | Request shape and traced bounds | What it does | Static safety |
|---|---|---|---|
| `FF A0` | `FF A0 a b c d operand operation`; table indices are not range-checked | Reads two internal lookup-table values and combines them: operation `1` add, `2` absolute difference, `3` multiply, `4` divide; returns the result in an A0 response | Avoid. It is not an LED command, has unchecked table indices, and operation `4` can divide by zero |
| `FF A1` | `FF A1 T I` + `67 RGB triplets`; 205 bytes total; useful `I = 1..0x0C` | Writes `67` entries at plane offset `0x42 * (I - 1)`. Index `0x0C` triggers `FUN_00030cd0(4, T, ..., 0x900)` and a display/commit path | Conditional only. RAM upload, but requires exact length, valid chunk sequence, and a captured/known `T` |
| `FF A3` | `FF A3 T I` + `51 RGB triplets`; 155 bytes total; useful `I = 1..0x10` | Writes `51` entries at offset `0x32 * (I - 1)`. Index `0x10` triggers the same commit mode | Conditional only; same restrictions as A1 |
| `FF A5` | `FF A5 T I` + `6 RGB triplets`; 22 bytes total; useful `I = 1..0x9A` | Writes `6` entries at offset `5 * (I - 1)`. Index `0x9A` triggers the same commit mode | Conditional only; same restrictions as A1 |
| `FF A9` | `FF A9 T I`; offset `5 * (I - 1)` | Starts frame output mode `3`, then fills a response from the RGB planes. The traced loop visits six entries, but the response declares `0x0F` payload bytes and transmits only `0x15` bytes, so the last triplet is truncated by the checksum | Conditional only; it is active output, not a passive read |
| `FF AA` | `FF AA T` is the meaningful prefix | Sends an `AA` acknowledgment and calls `FUN_00030cd0(3, T, 0, 0)`, which outputs the selected frame/table state | Conditional only; target range/meaning is unknown |
| `FF AB` | No fields beyond the opcode are consumed | Sends `FF AB 02 00 <checksum>` and clears the frame-active marker | Lowest-risk A* control statically, but still not runtime-confirmed as a universal stop |
| `FF AC` | `FF AC p2 p3 p4_hi p4_lo p6_hi p6_lo p8`; at least 9 bytes are required | Acknowledges, stores scheduler parameters, clamps the two 16-bit values to `0..0x2FF`/ordered range and `p8` to `0..10`, then schedules internal LED opcode `0xCE` | Conditional only; it actively changes the scheduler and its meaning is unresolved |
| `FF AE` | `FF AE T I`; offset `0x32 * (I - 1)` | Starts frame output mode `3`, then builds a medium readback. The loop visits 51 entries, while the transmitted payload is `0x96` bytes (50 complete RGB triplets) plus checksum | Conditional only; active output and internally inconsistent without a capture |
| `FF AF` | `FF AF T I`; offset `0x42 * (I - 1)` | Starts frame output mode `3`, then builds a large readback. The loop visits 67 entries, while the transmitted payload is `0xC6` bytes (66 complete RGB triplets) plus checksum | Conditional only; active output and internally inconsistent without a capture |

The upload branches have a bounds gate before each plane write (`offset + i <
0x300`), so an out-of-range chunk index does not directly write beyond the
three traced planes. That is not a reason to fuzz: the packet is still read at
fixed offsets, the terminal index controls a visible output action, and the
target selector is passed into the LED-controller command path.

The A1/A3/A5 branches emit a short five-byte acknowledgment of the general
shape `FF <opcode> I 00 <checksum>`. The decompiled checksum length is derived
from `I + 3` while the transmitted length remains five, so the response should
not be treated as a clean specification for a hand-written client. A known BLE
capture is needed to resolve that apparent protocol quirk.

### Practical operating boundary

For light/animation tinkering, keep every A* command out of the normal
allow-list. If custom frame upload becomes a goal, the least risky order is:

1. capture a complete official-client transaction and recover the real `T`;
2. replay one known-good `A1`/`A3`/`A5` sequence with all RGB bytes set to zero;
3. verify the acknowledgment and output after each chunk; and
4. only then change one RGB triplet at a time.

Do not send truncated packets, index `0`, guessed target values, or random
`A0`/`AC` fields. `A9`/`AE`/`AF` are not passive queries because they invoke the
frame output helper before constructing their response. `AA` is a playback
command, and `AB` is the only A* branch that looks like a pure cancel/ack
control in this static trace.

## Scope and next reverse-engineering targets

Static analysis proves that the additional opcodes are accepted by this BLE
handler. It does not prove that every opcode is reachable from the official
Android app, nor that every outgoing `ble_uart_write()` packet is visible as a
BLE notification; several are likely internal controller messages.

The most useful next artifacts would be:

- BLE captures while the official app changes modes, synchronizes a concert
  pattern, or updates settings;
- a second firmware image for comparison;
- captures of the UART/bridge side while sending `A*` or `C*` commands; and
- runtime tests with a recoverable configuration backup before trying `C*`
  commands.
